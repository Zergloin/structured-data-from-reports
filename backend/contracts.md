# Спецификация интерфейсов backend для ЛР2

Сигнатуры ниже являются проектными контрактами компонентов, а не реализацией Python. Все вызовы между компонентами одной схемы — `Python Call`, в том числе `async/await`. Сетевые протоколы применяются только на границе контейнера. Ошибки компонентов преобразуются в HTTP-ответы только контроллером.

## Общие типы

| Тип | Состав |
|---|---|
| `Principal` | `user_id: UUID`, роли и проверенные права на объект |
| `Upload` | поток байтов, имя и заявленный тип; фактический формат проверяется сервером |
| `DocumentVersion` | `document_version_id: UUID`, `object_key`, `checksum`, формат, автор, дата, метаданные |
| `SchemaVersion` | `schema_version_id: UUID`, `schema_id: UUID`, `revision: int`, JSON Schema, статус публикации |
| `JobSnapshot` | `job_id: UUID`, версии документа и схемы, статус, номер попытки, этап и последняя ошибка |
| `AttemptContext` | `job_id`, `attempt_no: int`, токен захвата и срок аренды; неизменяемые ссылки на версии |
| `ParsedDocument` | версия документа, текст и таблицы; фрагменты с `fragment_id`, текстом, опциональными `page` и `bbox` |
| `ExtractionCandidate` | JSON-значения, ссылки на фрагменты, модель и параметры вызова |
| `ValidationIssue` | JSON Pointer поля, код, сообщение, степень ошибки |
| `FieldSource` | путь поля, версия документа, `fragment_id`, проверенная цитата; координаты только при наличии |
| `DraftView` | `draft_id: UUID`, `draft_revision: int`, значения, источники, ошибки, `review_status` |
| `RecordVersion` | ID неизменяемой подтверждённой версии, значения, источники, версии схемы и документа, эксперт и время |

`UUID` обозначает идентификатор; JSON-значения включают `null`. Отсутствие значения не заменяется нулём или пустой строкой. Для черновика отсутствие обязательного поля допускается с ошибкой; при подтверждении проверяется полная схема.

## Прикладной сервер api

### api_controller и auth_comp

`require_principal(token: str, action: str, resource_id: UUID | None) -> Principal`

Контроллер передаёт учётные данные и требуемое действие. Компонент доступа проверяет пользователя, роли и доступ к объекту через `repository_comp`. Идентификатор автора берётся из результата проверки. Ошибки `Unauthorized` и `Forbidden` отображаются в HTTP 401 и 403.

Контроллер проверяет фиксированную структуру запроса Pydantic, вызывает прикладной компонент и преобразует его результат в DTO. Правила JSON Schema и транзакции в контроллере не реализуются.

### document_comp

`submit(upload: Upload, schema_version_id: UUID, actor: Principal) -> Submission`

До приёма проверяются права, доступность опубликованной схемы, допустимый размер и фактический формат DOCX либо PDF с текстовым слоем. `file_store_comp` сохраняет неизменяемый оригинал под новым `object_key` и вычисляет checksum. После успешной записи одна транзакция регистрирует `DocumentVersion`, создаёт задание через `job_comp` и его событие outbox. `Submission` содержит `document_version_id`, `job_id` и статус `queued`.

Ошибки: `UnsupportedFormat`, `InvalidDocument`, `SchemaNotPublished`, `StorageUnavailable`. При ошибке записи объекта задание не создаётся. При откате БД объект может остаться бесхозным; очистка выполняется по отсутствию ссылки в БД после защитного интервала.

### job_comp

`create(document_version_id: UUID, schema_version_id: UUID, actor: Principal, uow: UnitOfWork) -> JobSnapshot`

Вызывается при приёме документа в уже открытой транзакции. Проверяет существование версий и публикацию схемы. Сохраняет `queued` и событие outbox с `job_id`; самостоятельно не фиксирует общую транзакцию.

`get(job_id: UUID, actor: Principal) -> JobSnapshot`

Возвращает сохранённый статус с проверкой доступа; не опрашивает брокер как источник истины.

`retry(job_id: UUID, actor: Principal) -> JobSnapshot`

Администратор может повторить только `failed`. Одна транзакция проверяет состояние, создаёт следующую попытку, переводит задание в `queued` и добавляет новое событие outbox. `job_id` и версии сохраняются. Повтор не изменяет историю ошибок. Ошибки: `NotFound`, `Forbidden`, `InvalidJobState`. Возврат экспертом на обработку является отдельным решением проверки.

### review_comp и validation_comp

`get_draft(draft_id: UUID, actor: Principal) -> DraftView`

`save(draft_id: UUID, expected_revision: int, patch: JSON, actor: Principal) -> DraftView`

Сервис читает закреплённую схему и проверяет правки через `validate(values, schema, mode="draft") -> list[ValidationIssue]`. Репозиторий атомарно сравнивает ревизию, сохраняет изменения, ошибки, автора и новую ревизию. Неизвестные поля запрещены. Неисправленные обязательные поля сохраняются с ошибками. История источника и ручной правки сохраняется; цитата не считается доказательством изменённого значения автоматически. Ошибки: `NotFound`, `Forbidden`, `RevisionConflict`, `InvalidPatch`.

`confirm(draft_id: UUID, expected_revision: int, actor: Principal) -> RecordVersion`

Требуется роль эксперта и состояние `awaiting_review`. Сервис выполняет `validate(values, schema, mode="confirm")`, затем в одной транзакции повторно проверяет ревизию, создаёт неизменяемую подтверждённую версию, записывает решение и статус `confirmed`. При блокирующей ошибке подтверждение не выполняется. Ошибки: `RevisionConflict`, `ValidationFailed`, `InvalidReviewState`, `Forbidden`. Алгоритм проверки чистый: получает значения и схему, возвращает ошибки без доступа к БД или сети.

### repository_comp

`transaction() -> UnitOfWork` задаёт единицу транзакции PostgreSQL. Внутри неё доступны `register_document`, `insert_job_and_event`, `save_draft_if_revision`, `confirm_if_revision`, `schedule_retry` и чтение опубликованной схемы. При исключении изменения откатываются. Операции с ревизиями используют условную запись либо блокировку строки и сообщают о конфликте.

### file_store_comp

`put_original(upload: Upload) -> StoredObject` возвращает новый ключ, checksum и размер только после успешной записи S3-объекта. `get(object_key: str) -> bytes` возвращает оригинал. Ключи и реквизиты хранилища клиентом не задаются. Ошибки: `StorageUnavailable`, `ObjectNotFound`, `ChecksumMismatch`.

### dispatch_comp

`dispatch_pending(limit: int) -> DispatchSummary` читает ожидающие события через репозиторий, публикует Celery-задачу `process_document(job_id)` в `extraction` и отмечает событие доставленным после publisher confirm. Это фоновая корутина в процессе API, отдельный контейнер не вводится. Захват события защищён арендой; потеря процесса допускает повторную публикацию. Доставка — как минимум один раз, поэтому обработчик обязан подавлять дубликаты. Тело прикладного сообщения содержит только `job_id`; метаданные Celery и AMQP не являются бизнес-полями задания.

## Обработчик worker

### task_comp и pipeline_comp

`process_document(job_id: UUID) -> ProcessingOutcome`

Вход Celery вызывает конвейер, который захватывает актуальную попытку через репозиторий. Завершённое задание возвращает сохранённый результат; дубликат активной попытки не запускает параллельное извлечение. После чтения контекста конвейер получает оригинал, проверяет checksum, вызывает разбор, извлечение и проверку, сохраняет результат. ACK разрешён после фиксации результата либо устойчивого решения о повторе/окончательной ошибке. При недоступной БД сообщение не подтверждается как обработанное.

### parser_comp

`parse(content: bytes, media_type: str, document_version_id: UUID) -> ParsedDocument`

Docling выделяет текст и таблицы, формирует ID фрагментов. OCR в первой версии не включается. Координаты страницы и bbox возвращаются только при надёжном сопоставлении. Ошибки: `UnsupportedFormat`, `UnreadableDocument`, `TextLayerMissing`. Сохранение результата разбора выполняет конвейер через файловый адаптер.

### extractor_comp

`extract(parsed: ParsedDocument, schema: SchemaVersion, config: ModelConfig) -> ExtractionCandidate`

Передаёт выбранной модели OpenRouter схему и пронумерованные фрагменты, получает JSON-кандидат с источниками. Отсутствующие сведения представлены `null`. Сохраняются модель, параметры и сведения о провайдере. Тайм-аут, 429 и временные 5xx классифицируются как временная ошибка; недоступные учётные данные и неизменяемый некорректный запрос требуют исправления причины. Повтор ограничен. Конкретный алгоритм можно заменить в ЛР3 через Strategy, не меняя контракт.

### worker_validation_comp

`validate(candidate: ExtractionCandidate, schema: SchemaVersion, parsed: ParsedDocument) -> ValidatedDraft`

Проверяет типы и ограничения полей, отсутствие лишних ключей и связь источников с реальными фрагментами этой версии документа. Сопоставляет цитату с текстом. Возвращает значения, проверенные источники и ошибки. Ссылка на несуществующий фрагмент не сохраняется как подтверждённое доказательство. Формальная валидация не доказывает фактическую правильность значения. Исправимый результат с ошибками полей сохраняется для эксперта; неразбираемый ответ не считается готовым черновиком.

### worker_repository_comp

`claim(job_id: UUID) -> AttemptContext | ExistingResult | Busy`

`renew(context: AttemptContext) -> AttemptContext`

`complete(context: AttemptContext, draft: ValidatedDraft, artifacts: ArtifactRefs) -> DraftView`

Захват использует блокировку/условное изменение, токен попытки и ограниченную аренду. Конвейер продлевает аренду через `renew` во время долгой обработки. `complete` проверяет актуальность токена и одной транзакцией сохраняет черновик, источники, ошибки, сведения о модели и `succeeded`. Повторный вызов той же попытки возвращает готовый результат. Истёкшая попытка не перезаписывает более новую. `record_failure(context, error, retryable)` сохраняет ошибку и либо `failed`, либо следующую попытку с событием outbox; это событие публикует существующий `dispatch_comp` процесса API.

### worker_file_store_comp

`get_original(object_key: str, checksum: str) -> bytes`

`put_parsed(document: ParsedDocument, context: AttemptContext) -> ArtifactRefs`

Оригинал читается по ключу из контекста. Артефакты получают ключи, включающие версию документа и попытку. Ссылки на них фиксируются в транзакции результата. Ошибка S3 не допускает фиктивного завершения задания. Репозиторий и файловый адаптер могут иметь общую реализацию с API, но их экземпляры выполняются в другом процессе.

## Контракты для веб-клиента

| Операция | Запрос и результат | Ошибки |
|---|---|---|
| `POST /documents` | multipart: `file`, `schema_version_id`; 202: версия документа, `job_id`, `queued` | 401, 403, 413, 415, 422, 503 |
| `GET /jobs/{job_id}` | 200: статус, попытка, этап, ошибка, `draft_id` при готовности | 401, 403, 404 |
| `POST /jobs/{job_id}/retry` | 202: тот же `job_id`, новая попытка | 401, 403, 404, 409 |
| `GET /drafts/{draft_id}` | 200: значения, ревизия, ошибки и источники | 401, 403, 404 |
| `PATCH /drafts/{draft_id}` | JSON: `expected_revision`, `patch`; 200: новая ревизия | 401, 403, 404, 409, 422 |
| `POST /drafts/{draft_id}/confirm` | JSON: `expected_revision`; 201: подтверждённая версия | 401, 403, 404, 409, 422 |

Эти маршруты уточняются в ЛР2 как контракт backend. Ошибка имеет форму `{code, message, field_errors, trace_id}`; внутренние исключения и секреты клиенту не передаются. JSON Schema не заменяет Pydantic: первая проверяет изменяемую предметную схему, второй — фиксированные DTO API.

## Целостность и состояния

`queued -> running -> succeeded | failed` — техническое состояние задания. Для временной ошибки допускается `running -> queued` с новой попыткой и ограничением числа повторов. `awaiting_review -> confirmed | rejected` — состояние решения эксперта. Исправление подтверждённой записи создаёт новую версию, а не перезаписывает старую.

В обычной обработке один `job_id` даёт один актуальный результат. Повторная доставка сообщения не создаёт второй черновик; технические попытки имеют уникальный номер и сохраняются в истории. Экспертный возврат после `rejected` запускается отдельной операцией с сохранением истории, а не HTTP-маршрутом административного повтора `failed`.

Ключи подтверждённых версий, ревизии и условные записи защищают от потери правок. Вызов внешней модели может повториться при сбое между ответом модели и фиксацией БД; отсутствие повторного списания стоимости не гарантируется. ЛР2 фиксирует проектные решения. Реальные гарантии восстановления требуют проверки реализации на следующем этапе.
